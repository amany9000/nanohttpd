## Rollback plan
- **Criteria**: Critical protocol regressions, public API incompatibility beyond the approved versioning plan, build divergence, or unresolved high-severity dependency issue.
- **Steps**:
  1. Stop promotion of the candidate and keep the last stable coordinates available.
  2. Revert the affected dependency/module change or publish a corrected candidate.
  3. Notify consumers who opted into the candidate and document the resolution.
- **Maximum acceptable rollback time**: Not specified; library releases are opt-in, so no live traffic rollback window is assumed.
- **Owner**: Release manager / maintainer

## Go / no-go criteria
- **Go**:
  - All required parity and API compatibility checks pass for every included module.
  - Maven and Gradle build and publish equivalent artifacts.
  - Target Java baseline and dependency policy are documented, and no unresolved critical vulnerability/license issue remains.
  - Maintainer approves candidate release notes and migration guide.
- **No-go**:
  - Any unexplained protocol regression or API break outside the approved versioning policy.
  - Builds resolve materially different dependency graphs or fail on the declared Java baseline.
  - A critical vulnerability, incompatible license, or unsupported runtime constraint remains unresolved.

## Post-release
- [ ] Monitor issues and consumer feedback through at least one release cycle (duration to be set by maintainer).
- [ ] Validate compatibility according to `parity_specs.md` when generated by the Inspector.
- [ ] Deprecate old dependency lines/coordinates only according to the approved support horizon.

## Notes

No database migration, traffic routing, or service downtime is assumed. The cutover is adoption of versioned library artifacts by downstream applications.
